\subsection{Frontend}

Frontend của hệ thống thương mại điện tử được thiết kế với mục tiêu cân bằng giữa hiệu năng, khả năng mở rộng và tối ưu hóa cho công cụ tìm kiếm. Trong bối cảnh hệ thống có lưu lượng truy cập lớn và đa dạng thiết bị, frontend không chỉ đảm nhiệm vai trò hiển thị giao diện mà còn ảnh hưởng trực tiếp đến trải nghiệm người dùng và hiệu quả kinh doanh.

Từ yêu cầu đó, nhóm tiếp cận thiết kế frontend theo hướng ưu tiên rendering phía server, giảm tải JavaScript phía client và phân tách rõ trách nhiệm giữa hiển thị nội dung và tương tác người dùng. Các quyết định công nghệ được đưa ra dựa trên so sánh thực tế giữa các lựa chọn phổ biến, thay vì đơn thuần theo xu hướng.

\subsubsection{Ngôn ngữ và nền tảng}

\textbf{Lựa chọn framework frontend}

Ở tầng framework, ba hệ sinh thái phổ biến hiện nay là React, Angular và Vue. Angular cung cấp kiến trúc đầy đủ và chặt chẽ, phù hợp với các hệ thống enterprise có quy trình nghiêm ngặt, nhưng đổi lại là độ phức tạp cao và chi phí học tập lớn. Vue có cú pháp đơn giản và dễ tiếp cận, tuy nhiên hệ sinh thái cho các bài toán lớn như SSR, phân tách server--client và tối ưu SEO chưa đồng đều giữa các giải pháp.

React được lựa chọn nhờ tính linh hoạt cao và hệ sinh thái phong phú, cho phép xây dựng kiến trúc theo hướng tối ưu dần theo quy mô hệ thống. Đặc biệt, React không áp đặt cấu trúc cứng nhắc, phù hợp với các hệ thống cần mở rộng và thay đổi nhanh như thương mại điện tử.

\textbf{Next.js trên nền React}

Thay vì sử dụng React thuần với mô hình client-side rendering, nhóm lựa chọn Next.js để giải quyết các hạn chế về hiệu năng và SEO. Next.js hỗ trợ sẵn server-side rendering, static generation và incremental regeneration, giúp nội dung quan trọng được render sớm trên server thay vì chờ tải JavaScript phía client. So với các giải pháp tự cấu hình SSR, Next.js giảm đáng kể chi phí triển khai và rủi ro vận hành.

Việc sử dụng App Router và React Server Components cho phép phân tách rõ các thành phần chỉ cần hiển thị nội dung với các thành phần cần tương tác, từ đó giảm lượng JavaScript gửi xuống trình duyệt và cải thiện thời gian tải trang.

\textbf{Ngôn ngữ TypeScript}

Ở tầng ngôn ngữ, TypeScript được lựa chọn thay cho JavaScript thuần. Với hệ thống có nhiều luồng dữ liệu phức tạp như sản phẩm, đơn hàng và thanh toán, việc thiếu kiểm soát kiểu dữ liệu dễ dẫn đến lỗi logic khó phát hiện. TypeScript bổ sung định kiểu tĩnh, giúp phát hiện lỗi sớm, hỗ trợ refactor an toàn và tăng khả năng phối hợp giữa frontend và backend thông qua các hợp đồng dữ liệu rõ ràng.

\subsubsection{Giao diện và trải nghiệm người dùng}

\textbf{Chiến lược styling}

Các phương án phổ biến cho styling gồm CSS truyền thống, CSS-in-JS và utility-first CSS. CSS truyền thống dễ tiếp cận nhưng khó kiểm soát khi quy mô lớn. CSS-in-JS như styled-components giúp gắn style với component, nhưng tạo thêm chi phí runtime và phức tạp trong quá trình build.

Tailwind CSS được lựa chọn theo hướng utility-first nhằm kiểm soát trực tiếp style tại component, giảm CSS dư thừa và tránh xung đột class. Cách tiếp cận này giúp bundle CSS gọn nhẹ hơn và phù hợp với yêu cầu tối ưu hiệu năng của hệ thống thương mại điện tử.

\textbf{Thư viện giao diện}

Các thư viện UI đóng gói sẵn như Material UI hay Ant Design cung cấp nhiều component hoàn chỉnh, nhưng thường áp đặt style và hành vi mặc định, gây khó khăn khi tùy biến sâu. Nhóm lựa chọn shadcn/ui kết hợp Radix UI theo hướng headless, chỉ cung cấp hành vi và khả năng truy cập, không ràng buộc thiết kế.

Trade-off của cách tiếp cận này là cần đầu tư nhiều hơn vào xây dựng UI, nhưng đổi lại là khả năng kiểm soát hoàn toàn giao diện, đảm bảo tính nhất quán và tuân thủ chuẩn accessibility trong dài hạn.

\subsubsection{Quản lý trạng thái và dữ liệu}

\textbf{Server state}

Đối với dữ liệu lấy từ backend, các lựa chọn phổ biến gồm fetch thủ công, SWR và TanStack Query. Fetch thủ công đơn giản nhưng nhanh chóng trở nên phức tạp khi cần cache, retry và đồng bộ dữ liệu. SWR phù hợp cho các use case đơn giản, nhưng thiếu một số cơ chế kiểm soát nâng cao.

TanStack Query được lựa chọn nhờ cung cấp đầy đủ cache, deduplication, background refetch và quản lý vòng đời dữ liệu. Việc tách server state ra khỏi client state giúp frontend tập trung vào hiển thị, đồng thời giảm logic lặp lại trong code.

\textbf{Client state}

Đối với trạng thái cục bộ như giỏ hàng hoặc trạng thái giao diện, Redux, Context API và Zustand là các lựa chọn phổ biến. Redux mạnh nhưng nhiều boilerplate, Context API dễ dùng nhưng dễ gây re-render diện rộng.

Zustand được lựa chọn vì API gọn nhẹ, hiệu năng tốt và đủ đáp ứng nhu cầu của các state cục bộ mà không làm phức tạp kiến trúc tổng thể.

\subsubsection{Xử lý form và kiểm tra dữ liệu}

Formik và các form controlled truyền thống dễ triển khai nhưng phát sinh nhiều re-render khi form phức tạp. React Hook Form được lựa chọn nhờ tận dụng uncontrolled components, giúp cải thiện hiệu năng nhập liệu và đơn giản hóa code.

Đối với validation, Zod được chọn thay vì Yup hoặc Joi do khả năng tích hợp chặt chẽ với TypeScript. Việc định nghĩa schema duy nhất cho cả validation và typing giúp giảm sai lệch dữ liệu giữa frontend và backend.

\subsubsection{Build, DevOps và triển khai}

\textbf{Quản lý mã nguồn}

Kiến trúc monorepo được lựa chọn thay cho multi-repo nhằm thuận tiện trong việc chia sẻ code và đồng bộ dependency. Turborepo được ưu tiên nhờ cấu hình đơn giản và khả năng cache hiệu quả. pnpm được sử dụng để giảm trùng lặp dependency và tăng tốc cài đặt.

\textbf{Bundler}

Turbopack được sử dụng thay cho Webpack nhằm cải thiện tốc độ build và khởi động môi trường phát triển. Việc đánh đổi ở đây là hệ sinh thái plugin còn mới, nhưng lợi ích về tốc độ và khả năng tích hợp với Next.js phù hợp với định hướng dài hạn của dự án.

\textbf{Triển khai}

Hệ thống được triển khai trên Vercel thay vì tự quản lý hạ tầng truyền thống. Quyết định này giảm đáng kể chi phí vận hành và cấu hình, đồng thời tận dụng sẵn các tối ưu cho SSR, edge function và mạng CDN toàn cầu, phù hợp với đặc thù của frontend Next.js.
