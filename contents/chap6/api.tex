\subsection{Thiết kế API}

\subsubsection{Mục tiêu của thiết kế API}

Mục tiêu chung của việc thiết kế API là cung cấp điểm truy cập thống nhất cho ứng dụng frontend và đảm bảo tính nhất quán cho các giao dịch phân tán nội bộ.

Hệ thống triển khai hai loại API chính dựa trên mục đích sử dụng:

\begin{enumerate}
    \item External API (Frontend-Facing): Là các API công khai, phục vụ giao tiếp trực tiếp với ứng dụng frontend. Hầu hết các API này là điểm khởi đầu cho các luồng xử lý command hoặc kích hoạt một giao dịch phân tán.
    \item Internal API (Backend/Saga Orchestration): Là các API nội bộ, được gọi đồng bộ bởi orchestrator service để thực hiện các bước tuần tự của một giao dịch phân tán phức tạp. Các API này đảm bảo tính nhất quán giữa nhiều microservice theo mô hình Saga Orchestration.
\end{enumerate}

Việc thiết kế  API tuân theo các tiêu chí:

\begin{itemize}
    \item Đơn giản – rõ ràng – tách biệt theo domain.
    \item Phản hồi thống nhất theo cấu trúc BaseResponse.
    \item Request/Response chuẩn hóa thông qua DTO, không lộ dữ liệu nội bộ của service.
    \item Đảm bảo khả năng mở rộng, dễ thay đổi khi kiến trúc Cloud-Native kết hợp với Event Driven Architecture tăng số lượng tài nguyên.
\end{itemize}

Hầu hết các API trong hệ thống đều được thiết kế theo kiến trúc CQRS. Thay vì sử dụng một mô hình dữ liệu dùng chung, hệ thống tách biệt luồng ghi (command) và luồng đọc (query). Các thao tác thay đổi dữ liệu được thực thi trực tiếp vào cơ sở dữ liệu quan hệ để đảm bảo tính nhất quán tức thời, đồng thời phát đi các sự kiện nghiệp vụ qua Kafka để đồng bộ hóa với các dịch vụ khác.

Nhờ cơ chế này, API phản hồi kết quả dựa trên trạng thái thực tế của dữ liệu, trong khi các tác vụ phụ trợ hoặc phân tích sẽ được thực hiện bất đồng bộ bởi các consumer phía sau.

\subsubsection{Nguyên tắc thiết kế API}

Để đảm bảo một hệ thống API đồng bộ, dễ hiểu, dễ mở rộng và an toàn, việc tuân thủ một bộ các nguyên tắc thiết kế thống nhất là điều tối quan trọng. Các nguyên tắc dưới đây tập trung vào việc áp dụng mô hình Resource-Oriented và chuẩn mực RESTful cùng với các biện pháp bảo mật và quản lý phiên bản hiệu quả đối với các External API.
\begin{itemize}
    \item Theo mô hình Resource-Oriented (dựa trên tài nguyên: users, products, carts, orders…).
    \item RESTful: sử dụng GET/POST/PUT/DELETE.
    \item Áp dụng DTO cho mọi request/response, hạn chế lộ entity gốc.
    \item Sử dụng token-based authentication cho những API yêu cầu xác thực.
\end{itemize}

Internal API được thiết kế để đảm bảo độ tin cậy và khả năng hoàn tác (Compensation), khác biệt với External API.

\begin{itemize}
    \item Cấu trúc Endpoint: Mỗi service tham gia Saga phải cung cấp một cặp endpoint tương ứng với hành động Thực thi và Hoàn tác.
    \begin{itemize}
        \item Thực thi: $\text{POST}$ $\text{/api/internal/\{resource\}/execute}$
        \item Hoàn tác: $\text{POST}$ $\text{/api/internal/\{resource\}/compensate}$
    \end{itemize}
    \item Phản hồi:Phản hồi tập trung vào Mã trạng thái HTTP ($200/\text{201}$ cho thành công, $400/500$ cho thất bại) và dữ liệu tối thiểu cần thiết cho Orchestrator.
    \item Request Data: Luôn phải chứa $SagaID$ để theo dõi trạng thái.
\end{itemize}

\subsubsection{Cấu trúc mẫu của Request/Response trong API}

Để đảm bảo tính thống nhất giữa các microservice và giảm thiểu trùng lặp trong quá trình thiết kế API, hệ thống chuẩn hóa toàn bộ phản hồi và truy vấn phân trang thông qua ba lớp cơ sở: BaseResponse, BasePaginationResponse, và BasePaginationRequest. Các thành phần này đóng vai trò làm khuôn mẫu chung (template) được sử dụng xuyên suốt tất cả service nghiệp vụ (User, Product, Order, Cart, Admin, AI).

\textbf{\textit{a/ BaseResponse<T> – Cấu trúc phản hồi chuẩn }}

BaseResponse được sử dụng cho tất cả API không yêu cầu phân trang. Đây là cấu trúc phản hồi đơn giản nhưng thống nhất, giúp frontend xử lý kết quả và lỗi một cách dễ dàng.

Các trường thông tin:

\begin{itemize}
    \item status (int): Mã trạng thái HTTP hoặc mã nội bộ xác định kết quả xử lý, ví dụ: 200, 400, 404,...
    \item data (T): Payload chứa dữ liệu cần trả về cho frontend, có thể là DTO hoặc bất kỳ kiểu dữ liệu nào.
    \item message (String): Thông tin mô tả kết quả xử lý, ví dụ: "Success", "Invalid credentials".
\end{itemize}

Việc áp dụng các nguyên tắc này có ý nghĩa quan trọng trong việc chuẩn hóa giao diện API giữa các service, đảm bảo tính đồng nhất và khả năng tích hợp dễ dàng. Sự chuẩn hóa này cũng trực tiếp hỗ trợ logging và tracking dễ dàng hơn, giúp hệ thống theo dõi và xử lý lỗi hiệu quả. Hơn nữa, nó còn giúp giảm thiểu số lượng schema response lặp lại, tối ưu hóa mã nguồn và đơn giản hóa việc phát triển cho các ứng dụng client.

\textbf{\textit{BasePaginationResponse<T> – Cấu trúc phản hồi phân trang}}

BasePaginationResponse được sử dụng cho các API trả về danh sách có phân trang (ví dụ: danh sách sản phẩm, danh sách đơn hàng, danh sách người dùng admin).

Lớp này mở rộng cấu trúc BaseResponse bằng cách bổ sung các thông tin phân trang cần thiết.

Các trường thông tin:

\begin{itemize}
    \item status (int): Mã trạng thái HTTP hoặc mã nội bộ xác định kết quả xử lý, ví dụ: 200, 400, 404,\dots
    \item page\_number (int): Số trang hiện tại (zero-based).
    \item page\_size (int): Số lượng item trên mỗi trang.
    \item count\_items (long): Tổng số item lấy được từ truy vấn.
    \item count\_pages (int): Tổng số trang có thể hiển thị.
    \item data (T): Payload chứa dữ liệu cần trả về cho frontend, có thể là DTO hoặc bất kỳ kiểu dữ liệu nào.
    \item message (String): Thông tin mô tả kết quả xử lý, ví dụ: "Success", "Invalid credentials".
\end{itemize}

Việc thống nhất cơ chế phân trang mang lại ý nghĩa then chốt là chuẩn hóa mọi API phân trang trên các service, tạo ra một giao diện đồng nhất. Điều này không chỉ giúp frontend hiển thị giao diện phân trang (paginated UI) dễ dàng hơn nhờ vào cấu trúc response đã được định trước, mà còn hỗ trợ backend sử dụng các công cụ như Spring Data xây dựng phân trang hiệu quả và nhất quán xuyên suốt hệ thống.

\textbf{\textit{BasePaginationRequest – Chuẩn hóa Request phân trang}}

BasePaginationRequest là lớp DTO dùng cho toàn bộ API cần phân trang. Lớp này hỗ trợ Spring Data trực tiếp thông qua hàm toPageable(), giúp code service gọn và tránh lặp lại logic phân trang.

Các trường thông tin:
\begin{itemize}
    \item page (int): Chỉ số trang (bắt đầu từ 0). Có validate là không được nhỏ hơn 0.
    \item size (int): Số lượng phần tử mỗi trang. Có validate là không được nhỏ hơn 1.
    \item sortBy (String): Tên trường cần sắp xếp.
    \item sortDirection (String): Hướng sắp xếp: "ASC" hoặc "DESC" (mặc định "DESC").
\end{itemize}

Việc chuẩn hóa cách thức backend nhận yêu cầu phân trang giúp tăng tính nhất quán giữa các API khác nhau, đảm bảo mọi dịch vụ đều xử lý yêu cầu phân trang theo cùng một quy tắc. Điều này cho phép tái sử dụng logic phân trang đã được định nghĩa trong hầu hết mọi service, từ đó tiết kiệm thời gian phát triển và giảm thiểu lỗi.

\subsubsection{User Service}

User Service chịu trách nhiệm quản lý thông tin người dùng, xác thực tài khoản và cung cấp token để frontend truy cập các chức năng khác trong hệ thống. Do số lượng API đầy đủ khá lớn, mục này chỉ trình bày các API đại diện cho nhóm chức năng Authentication \& Account Management – nhóm quan trọng nhất của User Service.

\textbf{1. POST /api/auth/login/local}
\begin{itemize}
    \item Chức năng: Xác thực người dùng bằng email/mật khẩu.
    \item Đầu vào: Thông tin đăng nhập (email, password).
    \item Xử lý (Command):
    \begin{enumerate} 
        \item Xác thực thông tin đăng nhập từ cơ sở dữ liệu chính. 
        \item Sinh access token và refresh token cho phiên làm việc. 
        \item Gửi Domain Event \textit{UserLoggedIn} sang Kafka phục vụ phân tích hành vi. 
    \end{enumerate}
    \item Đầu ra: Token phiên làm việc và phản hồi đăng nhập thành công.
\end{itemize}

\textbf{2. GET /api/user/profile/me}
\begin{itemize}
    \item Chức năng: Lấy thông tin hồ sơ của khách hàng đang đăng nhập.
    \item Đầu vào: Access token trong header yêu cầu.
    \item Xử lý (Query):
    \begin{enumerate} 
        \item Giải mã và kiểm tra tính hợp lệ của token. 
        \item Truy vấn trực tiếp từ cơ sở dữ liệu người dùng thông qua ReadOnlyRepository bằng SQL thuần để tối ưu hiệu năng. 
    \end{enumerate}
    \item Đầu ra: Hồ sơ người dùng hiện tại (DTO).
\end{itemize}

\textbf{3. POST /api/auth/register/local}
\begin{itemize}
    \item Chức năng: Khởi tạo tài khoản mới bằng email và mật khẩu.
    \item Đầu vào: Email, password và thông tin người dùng.
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ và trùng lặp của email.
        \item Lưu thông tin người dùng mới trực tiếp vào cơ sở dữ liệu PostgreSQL thông qua JpaRepository.
        \item Phát sự kiện \textit{UserRegistered} sang Kafka để các dịch vụ khác (gợi ý sản phẩm, loyalty, notification, \dots) tiếp nhận xử lý bất đồng bộ.
    \end{enumerate}
    \item Đầu ra: Xác nhận đăng ký thành công. Tài khoản có thể sử dụng để đăng nhập ngay lập tức do dữ liệu đã được cập nhật vào cơ sở dữ liệu chính.
\end{itemize}

\subsubsection{Order Service}

Order Service chịu trách nhiệm quản lý đơn hàng và cập nhật trạng thái giao dịch. Theo mô hình kiến trúc CQRS, mọi yêu cầu thay đổi trạng thái được cập nhật trực tiếp vào cơ sở dữ liệu chính thông qua luồng ghi (Command), trong khi luồng đọc (Query) truy vấn trực tiếp từ các bảng dữ liệu đã tối ưu để phản hồi nhanh chóng cho frontend. Phần này giới thiệu các API tiêu biểu thuộc nhóm chức năng Order Placement \& Order Management.

\textbf{1. POST /api/order/create}
\begin{itemize}
    \item Chức năng: Tạo đơn hàng mới từ giỏ hàng hoặc từ yêu cầu mua ngay.
    \item Đầu vào: Thông tin sản phẩm, số lượng, địa chỉ giao hàng, phương thức thanh toán, \ldots.
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ của yêu cầu tạo đơn và dữ liệu khách hàng.
        \item Khởi tạo và lưu thông tin đơn hàng với trạng thái \texttt{PENDING} trực tiếp vào cơ sở dữ liệu PostgreSQL.
        \item Phát sự kiện \textit{OrderCreated} sang Kafka để các dịch vụ khác (Inventory, Payment, Cart) tiếp nhận xử lý trong quy trình Saga.
    \end{enumerate}
    \item Đầu ra: Xác nhận tạo đơn thành công kèm mã đơn hàng (\texttt{orderId}).
\end{itemize}

\textbf{2. GET /api/order/my-orders}
\begin{itemize}
    \item Chức năng: Lấy danh sách đơn hàng của người dùng hiện đang đăng nhập.
    \item Đầu vào: Access token để xác định danh tính người dùng.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Giải mã token để lấy \texttt{userId}.
        \item Sử dụng \texttt{Spring JdbcTemplate} truy vấn trực tiếp cơ sở dữ liệu để trả về danh sách đơn hàng dưới dạng DTO tối ưu.
    \end{enumerate}
    \item Đầu ra: Danh sách đơn hàng của người dùng với thông tin rút gọn (trạng thái, tổng tiền, ngày tạo, \ldots).
\end{itemize}

\textbf{3. GET /api/order/detail/\{orderId\}}
\begin{itemize}
    \item Chức năng: Lấy thông tin chi tiết của một đơn hàng cụ thể.
    \item Đầu vào: \texttt{orderId} được truyền qua URL; access token để xác định quyền truy cập.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Kiểm tra quyền xem đơn hàng (đảm bảo đơn thuộc về người dùng hiện tại hoặc quản trị viên).
        \item Truy vấn trực tiếp từ cơ sở dữ liệu các thông tin chi tiết bao gồm danh sách sản phẩm, giá, địa chỉ giao hàng và lịch sử trạng thái đơn hàng.
    \end{enumerate}
    \item Đầu ra: Thông tin chi tiết đơn hàng theo trạng thái hiện tại trong hệ thống.
\end{itemize}

\subsubsection{Cart Service}

Cart Service chịu trách nhiệm quản lý giỏ hàng của người dùng, bao gồm thêm sản phẩm, cập nhật số lượng và xoá khỏi giỏ. Theo mô hình kiến trúc CQRS, mọi thao tác thay đổi dữ liệu được thực hiện trực tiếp trên cơ sở dữ liệu chính, đảm bảo trạng thái giỏ hàng luôn được cập nhật tức thời để phục vụ cho người dùng.

\textbf{1. POST /api/cart/add}
\begin{itemize}
    \item Chức năng: Thêm một sản phẩm vào giỏ hàng của người dùng.
    \item Đầu vào: Thông tin sản phẩm (\texttt{productId}), số lượng, biến thể (nếu có), \dots
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ của sản phẩm và số lượng khả dụng.
        \item Cập nhật hoặc thêm mới bản ghi sản phẩm vào bảng \texttt{cart\_items} trong cơ sở dữ liệu PostgreSQL.
        \item Phát sự kiện nghiệp vụ sang Kafka để \texttt{Product Service} thực hiện cập nhật tồn kho dự kiến (reserve) hoặc kiểm tra lại điều kiện mở rộng.
    \end{enumerate}
    \item Đầu ra: Xác nhận sản phẩm đã được thêm vào giỏ hàng thành công.
\end{itemize}

\textbf{2. PUT /api/cart/increase/\{productId\}}
\begin{itemize}
    \item Chức năng: Tăng số lượng sản phẩm cụ thể trong giỏ hàng.
    \item Đầu vào: \texttt{productId} trên đường dẫn; số lượng tăng (mặc định là 1 nếu không truyền).
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra sự tồn tại của sản phẩm trong giỏ hàng của người dùng.
        \item Cập nhật trực tiếp số lượng mới vào cơ sở dữ liệu thông qua \texttt{JpaRepository}.
        \item Phát sự kiện thông báo thay đổi số lượng qua Kafka để đồng bộ hóa tồn kho dự kiến.
    \end{enumerate}
    \item Đầu ra: Xác nhận số lượng sản phẩm trong giỏ đã được cập nhật tăng.
\end{itemize}

\textbf{3. DELETE /api/cart/remove/\{productId\}}
\begin{itemize}
    \item Chức năng: Xóa hoàn toàn một sản phẩm khỏi giỏ hàng.
    \item Đầu vào: \texttt{productId} định danh sản phẩm cần xóa.
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ và sự tồn tại của sản phẩm trong giỏ.
        \item Thực hiện xóa bản ghi tương ứng trong bảng \texttt{cart\_items} tại cơ sở dữ liệu.
        \item Phát sự kiện để các dịch vụ liên quan thực hiện hoàn trả lại tồn kho dự kiến (nếu có).
    \end{enumerate}
    \item Đầu ra: Xác nhận sản phẩm đã được loại bỏ khỏi giỏ hàng thành công.
\end{itemize}

\subsubsection{Product Service}

Product Service chịu trách nhiệm quản lý thông tin sản phẩm, bao gồm danh mục, tồn kho, biến thể và dữ liệu hiển thị trên frontend. Theo mô hình CQRS, các yêu cầu truy vấn dữ liệu (Query) được thực hiện trực tiếp trên cơ sở dữ liệu đã tối ưu hóa thông qua luồng đọc chuyên biệt, giúp đảm bảo tốc độ phản hồi nhanh và khả năng chịu tải cao cho các trang danh mục và tìm kiếm.

\textbf{1. GET /api/product/list}
\begin{itemize}
    \item Chức năng: Lấy danh sách sản phẩm theo phân trang để hiển thị trên trang chủ hoặc trang danh mục.
    \item Đầu vào: Tham số phân trang (\texttt{page}, \texttt{size}) và tùy chọn sắp xếp.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Tiếp nhận các tham số phân trang từ request và chuyển đổi thành đối tượng \texttt{Pageable}.
        \item Sử dụng \texttt{Spring JdbcTemplate} truy vấn trực tiếp từ cơ sở dữ liệu để lấy các trường thông tin cần thiết: tên, giá, tồn kho, danh mục và hình ảnh.
        \item Áp dụng các bộ lọc hoặc sắp xếp theo yêu cầu của người dùng.
    \end{enumerate}
    \item Đầu ra: Danh sách sản phẩm theo trang kèm metadata phân trang chuẩn \texttt{BasePaginationResponse}.
\end{itemize}

\textbf{2. GET /api/product/search}
\begin{itemize}
    \item Chức năng: Tìm kiếm sản phẩm theo từ khóa, danh mục hoặc nhiều điều kiện lọc.
    \item Đầu vào: \texttt{keyword}, \texttt{categoryId}, \texttt{priceRange}, \texttt{sortBy}, \texttt{page/size}.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Áp dụng kỹ thuật tìm kiếm mờ (fuzzy matching) hoặc tìm kiếm toàn văn theo từ khóa.
        \item Thực hiện lọc dữ liệu theo danh mục, khoảng giá và trạng thái hoạt động trực tiếp tại tầng cơ sở dữ liệu.
        \item Truy vấn dữ liệu đã được tối ưu hóa cho mục đích tìm kiếm để trả về kết quả nhanh chóng.
    \end{enumerate}
    \item Đầu ra: Danh sách sản phẩm phù hợp cùng thông tin phân trang.
\end{itemize}

\textbf{3. GET /api/product/inventory/\{productId\}}
\begin{itemize}
    \item Chức năng: Kiểm tra tồn kho của một sản phẩm phục vụ cho quy trình giỏ hàng hoặc đặt hàng.
    \item Đầu vào: \texttt{productId} của sản phẩm cần kiểm tra.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Truy vấn trực tiếp số lượng tồn kho thực tế từ bảng kho hàng trong PostgreSQL.
        \item Tính toán số lượng khả dụng dựa trên số lượng tồn thực tế trừ đi các giao dịch đang chờ xử lý (inventory reservation).
    \end{enumerate}
    \item Đầu ra: Số lượng tồn kho chi tiết và trạng thái khả dụng của sản phẩm.
\end{itemize}

\subsubsection{Admin Service}

Admin Service chịu trách nhiệm cung cấp các chức năng phục vụ quản trị hệ thống, bao gồm truy xuất báo cáo, theo dõi hoạt động bán hàng và ghi nhận nhật ký thao tác của quản trị viên. Dịch vụ này tập trung vào việc xử lý dữ liệu tổng hợp từ nhiều nguồn thông qua cơ chế bất đồng bộ để tối ưu hiệu năng.

\textbf{1. POST /api/admin/report/product/generate}
\begin{itemize}
    \item Chức năng: Tạo yêu cầu thống kê sản phẩm bán ra trong một khoảng thời gian.
    \item Đầu vào:
    \begin{itemize}
        \item \texttt{startDate, endDate}: khoảng thời gian cần thống kê.
        \item \texttt{productId} (tùy chọn): mã sản phẩm cụ thể cần thống kê.
        \item \texttt{format}: định dạng xuất báo cáo (json, csv).
    \end{itemize}
    \item Xử lý (Command):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ của tham số đầu vào.
        \item Lưu yêu cầu vào bảng \texttt{report\_requests} trong PostgreSQL với trạng thái \texttt{PENDING}.
        \item Phát sự kiện yêu cầu báo cáo sang Kafka để Worker xử lý bất đồng bộ.
        \item Worker thực hiện thu thập dữ liệu từ các dịch vụ liên quan, lưu kết quả vào cơ sở dữ liệu báo cáo chuyên biệt (\texttt{ReportDB}) và cập nhật trạng thái thành \texttt{COMPLETED}.
        \item Ghi nhật ký thao tác quản trị vào cơ sở dữ liệu nhật ký.
    \end{enumerate}
    \item Đầu ra: Mã \texttt{reportId} và trạng thái khởi tạo yêu cầu.
\end{itemize}

\textbf{2. GET /api/admin/report/product/\{reportId\}}
\begin{itemize}
    \item Chức năng: Lấy kết quả báo cáo sản phẩm đã được khởi tạo.
    \item Đầu vào: \texttt{reportId} cần truy vấn.
    \item Xử lý (Query):
    \begin{enumerate}
        \item Truy vấn dữ liệu từ cơ sở dữ liệu báo cáo dựa trên \texttt{reportId}.
        \item Nếu trạng thái là \texttt{COMPLETED}, trả về kết quả thống kê bao gồm doanh thu, số lượng bán và danh sách chi tiết.
        \item Nếu báo cáo chưa hoàn tất, trả về trạng thái xử lý hiện tại (\texttt{PENDING} hoặc \texttt{PROCESSING}).
        \item Ghi nhật ký truy cập báo cáo của quản trị viên.
    \end{enumerate}
    \item Đầu ra: Dữ liệu báo cáo chi tiết hoặc trạng thái xử lý hiện hành.
\end{itemize}

\subsubsection{Orchestrator Service}

Orchestrator service là một microservice đặc biệt, đóng vai trò là "nhạc trưởng" trong các giao dịch phân tán phức tạp (Saga). Dịch vụ này không chịu trách nhiệm xử lý nghiệp vụ đơn lẻ mà tập trung vào việc điều phối chuỗi gọi internal API đồng bộ để đảm bảo tính nhất quán dữ liệu giữa nhiều microservice.

\textbf{1. POST /api/order/place}

API này là điểm tiếp nhận yêu cầu đặt hàng từ Frontend, đồng thời kích hoạt luồng Saga Orchestration để thực hiện giao dịch phân tán.

\begin{itemize}
    \item Chức năng: Khởi tạo luồng giao dịch đặt hàng (Order placement saga).
    \item Đầu vào: Thông tin đơn hàng (item, quantity, shippingAddress, paymentMethod, \dots).
    \item Xử lý (Orchestrator logic):
    \begin{enumerate}
        \item Kiểm tra tính hợp lệ của dữ liệu đầu vào (Validation).
        \item Ghi nhận nhật ký giao dịch \textit{SagaStarted} với trạng thái \texttt{PENDING} vào cơ sở dữ liệu Saga (\texttt{SagaLogDB}).
        \item Thực hiện chuỗi gọi internal API đồng bộ theo thứ tự (Saga steps): 
        \begin{itemize}
            \item Bước 1 (Giữ hàng): Gọi \texttt{Product Service} (\texttt{POST /api/internal/product/reserve}) để giữ tồn kho trong cơ sở dữ liệu.
            \item Bước 2 (Thanh toán \& Tạo đơn): Nếu bước 1 thành công, gọi \texttt{Order Service} (\texttt{POST /api/internal/order/process-payment}) để xử lý thanh toán và tạo đơn hàng chính thức.
            \item Kết thúc Saga: Nếu tất cả các bước đồng bộ thành công, Orchestrator cập nhật trạng thái Saga thành \texttt{COMPLETED} và phát sự kiện \textit{OrderPlacementCompleted} vào Kafka để thông báo cho toàn hệ thống.
            \item Hoàn tác (Compensation): Nếu bất kỳ bước nào thất bại (nhận mã lỗi HTTP 4xx hoặc 5xx), Orchestrator ngay lập tức kích hoạt chuỗi hoàn tác bằng cách gọi các Compensate API tương ứng (ví dụ: \texttt{/api/internal/product/compensate}) để khôi phục trạng thái dữ liệu trong DB.
        \end{itemize}
    \end{enumerate}
    \item Đầu ra: \texttt{BaseResponse} xác nhận đã kích hoạt Saga thành công (bao gồm \texttt{orderId} và trạng thái \texttt{PROCESSING}), hoặc thông báo lỗi nếu thất bại ngay từ bước kiểm tra đầu tiên.
\end{itemize}
